# agent-status 사용 규칙

## 목적

`agent-status` 문서는 세션이 끊기거나 새 세션을 열었을 때, 최소 토큰으로 현재 작업 위치를 복구하기 위한 동적 상태 문서다.

이 디렉터리의 문서는 정적 운영 규칙 문서와 다르다.

- 정적 문서
  - `AGENTS.md`
  - `docs/multi-agent-cli-operations.md`
  - `docs/agent-roles.md`
  - `docs/worktree-and-session-setup.md`
- 동적 문서
  - `docs/agent-status/*.md`

## 파일 구성

각 에이전트별로 문서 하나씩 유지한다.

- `orchestrator.md`
- `backend-agent.md`
- `frontend-agent.md`
- `verification-agent.md`

즉, 메인 에이전트 1개와 서브 에이전트 3개 기준으로 총 4개가 필요하다.

## agent id 기록 원칙

- `agent-status` 문서는 역할 상태를 관리하는 문서다.
- agent id는 영구 식별자가 아니라 세션 한정 정보로 취급한다.
- 필요하면 현재 활성 agent id를 기록할 수 있지만, 새 세션이 시작되면 그대로 재사용된다고 가정하지 않는다.
- 따라서 이 문서의 핵심은 "어떤 역할이 살아 있어야 하는가"와 "어떤 작업 상태였는가"이지, 과거 agent id 목록을 누적하는 것이 아니다.

## 생명주기 원칙

- 서브 에이전트는 태스크마다 새로 만드는 것이 아니라 오케스트레이터 세션 동안 재사용한다.
- 세션이 종료될 때 오케스트레이터가 해당 세션의 서브 에이전트를 함께 종료한다.
- 새 오케스트레이터 세션은 필요한 역할의 서브 에이전트를 새로 생성한다.
- 새 세션은 `agent-status`를 읽고 역할과 현재 작업 위치를 복구한다.
- 이전 세션의 서브 에이전트가 남아 있더라도 그것을 복구 대상으로 간주하지 않는다.

## 작성 원칙

- 짧게 유지한다
- 세션 복구에 필요한 정보만 남긴다
- 오래된 내용은 덧붙이지 말고 교체한다
- 작업 로그처럼 길게 누적하지 않는다
- 코드/명령/경로/브랜치명은 영어 그대로 유지한다

## 각 문서에 반드시 포함할 항목

- 마지막 갱신 시각
- 상태: `idle` / `active` / `blocked` / `done`
- 현재 작업
- 현재 브랜치
- 현재 worktree 경로
- 현재 worktree 상태: `exists` / `not-created`
- 현재 소유 범위
- 지금 수정 가능한 파일
- 지금 수정하면 안 되는 파일
- 마지막 결정
- 다음 액션 1~3개
- 막힌 점 또는 확인 필요 사항
- 세션 재개 시 먼저 볼 파일

## 세션 복귀 절차

새 세션을 시작할 때는 다음 순서로 읽는다.

1. `AGENTS.md`
2. `docs/multi-agent-cli-operations.md`
3. `docs/agent-roles.md`
4. `docs/agent-status/orchestrator.md`
5. 자신의 `docs/agent-status/<agent>.md`

가능하면 이 5개만 읽고 현재 작업을 복구할 수 있어야 한다.

## 최소 복구 기준

새 세션은 아래 질문에 문서만으로 바로 답할 수 있어야 한다.

- 지금 내가 어떤 역할인가
- 현재 진행 중인 작업이 있는가
- 내가 다시 생성해야 할 역할 에이전트는 무엇인가
- 현재 실제로 존재하는 `worktree`는 무엇인가
- 다음 액션은 무엇인가
- 덮어쓰면 안 되는 파일은 무엇인가

위 질문에 즉시 답할 수 없다면 `agent-status` 갱신이 부족한 상태로 본다.

## 오케스트레이터 전용 추가 규칙

- `orchestrator.md`에는 현재 활성 역할, 다시 생성해야 할 역할, 역할별 현재 상태를 항상 포함한다.
- `orchestrator.md`에는 현재 세션에서 활성화한 역할과 남은 작업을 항상 짧게 유지한다.
- 세션 종료 전에 어떤 서브 에이전트를 종료했는지까지 기록할 필요는 없지만, 다음 세션이 다시 띄워야 할 역할은 명확히 적어야 한다.
- 역할별 활성 에이전트는 세션당 1개를 기본으로 하며, 중복 생성은 예외 상황에서만 허용한다.
- 오케스트레이터가 직접 코드 구현을 했다는 상태를 남기지 않는다. 그런 상황 자체를 운영 위반으로 본다.
- 구현 변경이 생겼다면 반드시 해당 역할 문서 `backend-agent.md`, `frontend-agent.md`, `verification-agent.md` 중 하나에 작업 흔적이 남아 있어야 한다.
