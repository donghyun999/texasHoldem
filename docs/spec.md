# 텍사스 홀덤 토너먼트 MVP 명세서 v1

- 작성일: 2026-04-06
- 목적: 캐시 게임이 아닌 블라인드 상승형 단일 테이블 토너먼트 MVP를 실제 구현 가능한 수준으로 정의한다.
- 원본: `텍사스홀덤_토너먼트_MVP_명세서_v1.docx`

## 1. 문서 범위

본 문서는 단일 테이블 Sit and Go 토너먼트를 대상으로 한다.

- 최대 참가 인원은 9명이다.
- 블라인드는 일정 시간마다 상승한다.
- 플레이어는 토너먼트 도중 탈락할 수 있다.
- 마지막 1인이 남으면 토너먼트가 종료된다.
- 서버 authoritative 구조를 전제로 한다.
- 클라이언트는 서버 상태를 표시하고 액션만 전송한다.

## 2. 핵심 결론

토너먼트 모드에서는 올인과 사이드팟을 제외한 채 규칙을 유지하기 어렵다. 블라인드가 상승하면 짧은 스택 플레이어가 현재 콜 금액을 맞출 수 없는 상황이 반복적으로 발생하기 때문이다.

따라서 토너먼트 MVP는 단순 캐시 게임 MVP와 달리 올인과 사이드팟을 포함해야 한다. 대신 범위 통제를 위해 다음 범위 제한을 둔다.

- 단일 테이블만 지원한다.
- 리바이 없음
- 애드온 없음
- 멀티테이블 없음

## 3. MVP 목표

- 게스트 기반으로 토너먼트 테이블에 입장할 수 있어야 한다.
- `READY` 상태인 플레이어 2명 이상이 모이면 owner가 토너먼트를 시작할 수 있어야 한다.
- 토너먼트 시작 후 플레이어 스택은 핸드 간 누적되어야 한다.
- 블라인드는 정해진 레벨에 따라 자동 상승해야 한다.
- 플레이어는 `fold`, `check`, `call`, `bet`, `raise`, `all-in` 액션을 수행할 수 있어야 한다.
- 서버는 메인 팟과 사이드팟을 계산하고 쇼다운 결과를 정산할 수 있어야 한다.
- 마지막 1인이 남으면 우승자를 선언하고 토너먼트를 종료해야 한다.

## 4. MVP 제외 범위

- 회원가입, 로그인, 소셜 인증
- 관전자 모드
- 리바이, 애드온, 재진입
- 멀티테이블 토너먼트와 테이블 병합
- ICM, 상금 분배, 랭킹 포인트
- 채팅, 친구, 전적 저장
- 고급 재접속 복구와 타임뱅크

## 5. 용어 정의

- `tournament`: 시작부터 종료까지 하나의 우승자를 뽑는 경기 단위
- `level`: 일정 시간 동안 유지되는 블라인드 구간
- `small blind`, `big blind`: 각 핸드 시작 시 강제로 지불하는 기본 베팅
- `stack`: 플레이어가 현재 보유한 칩 수
- `main pot`: 모든 생존 플레이어가 공통으로 경쟁하는 팟
- `side pot`: 일부 플레이어만 추가로 경쟁하는 별도 팟
- `busted out`: 스택이 0이 되어 토너먼트에서 탈락한 상태

## 6. 토너먼트 구조

- 토너먼트는 1개의 테이블만 사용한다.
- 테이블 수용 인원은 2명 이상 9명 이하이다.
- 시작 전 상태는 `WAITING`이다.
- 시작 후에는 `IN_HAND`와 `HAND_RESULT`를 반복한다.
- 생존 플레이어가 1명이 되면 `FINISHED`로 전환된다.
- 시작 스택은 모든 참가자에게 2000칩으로 동일하게 부여한다.
- 이 스택은 핸드 종료 후에도 유지된다.
- owner는 토너먼트 생성자이며 시작 권한을 가진다.
- owner가 나가면 seated 상태 플레이어 중 `seatIndex`가 가장 작은 플레이어에게 권한을 넘긴다.

## 7. 게스트 및 참가 정책

- 사용자는 `guestId`와 `nickname`으로 식별된다.
- `guestId`는 `localStorage`에 저장한다.
- 동일 `guestId`는 동시에 하나의 토너먼트에만 참여할 수 있다.
- 동일 토너먼트 안에서는 닉네임 중복을 허용하지 않는다.
- 토너먼트가 `WAITING`일 때만 신규 입장이 가능하다.
- 이미 `IN_HAND` 이상 상태가 된 뒤에는 신규 입장을 허용하지 않는다.
- 리바이와 재진입은 MVP에서 지원하지 않는다.
- 탈락한 사용자는 같은 토너먼트에 다시 들어올 수 없다.

## 8. 플레이어 상태

플레이어 상태는 다음과 같이 관리한다.

- `LOBBY`
- `SEATED`
- `READY`
- `ACTIVE`
- `FOLDED`
- `ALL_IN`
- `BUSTED_OUT`
- `DISCONNECTED`

상태 의미는 다음과 같다.

- `READY`: 토너먼트 시작 전 참가 의사를 표현하는 상태
- `ACTIVE`: 현재 핸드에 참여 중이며 액션 가능성이 남아 있는 상태
- `FOLDED`: 현재 핸드에서 폴드한 상태
- `ALL_IN`: 현재 핸드에서 남은 스택 전부를 걸어 더 이상 추가 액션은 할 수 없지만 쇼다운 대상에는 포함되는 상태
- `BUSTED_OUT`: 스택이 0이어서 토너먼트 전체에서 탈락한 상태
- `DISCONNECTED`: 연결이 끊긴 상태. `WAITING`에서는 즉시 제거하고, 핸드 중에는 자동 폴드 또는 강제 올인 상태 이후 종료 시 정리한다.

## 9. 시작 조건

- 토너먼트 시작은 `WAITING` 상태에서만 가능하다.
- `READY` 상태인 플레이어가 2명 이상이어야 한다.
- owner가 시작 요청을 보내야 한다.
- 시작 시 `READY` 플레이어 전원에게 2000칩을 부여하고 `ACTIVE` 후보로 등록한다.
- `READY`가 아닌 플레이어는 토너먼트에 참가하지 못한다.

## 10. 블라인드 레벨 정책

- 블라인드는 시간 기반으로 상승한다.
- 서버는 토너먼트 시작 시 레벨 타이머를 시작한다.
- 레벨 변경은 핸드 도중 즉시 반영하지 않고 다음 핸드 시작 시 적용한다.
- 현재 레벨, 다음 레벨, 다음 레벨까지 남은 시간은 전체 테이블에 브로드캐스트한다.

기본 블라인드 레벨은 다음과 같다.

| 레벨 | 스몰 블라인드 | 빅 블라인드 | 지속 시간 |
| --- | --- | --- | --- |
| 1 | 10 | 20 | 5분 |
| 2 | 15 | 30 | 5분 |
| 3 | 25 | 50 | 5분 |
| 4 | 50 | 100 | 5분 |
| 5 | 75 | 150 | 5분 |
| 6 | 100 | 200 | 5분 |

## 11. 핸드 시작 규칙

- 각 핸드는 `BUSTED_OUT`이 아닌 플레이어 중 seated 상태를 유지한 플레이어만 대상으로 한다.
- 실제 핸드 참여자는 스택이 0보다 큰 플레이어다.
- 활성 플레이어가 2명 미만이면 새 핸드를 시작하지 않고 토너먼트를 종료한다.
- 딜러 버튼은 생존 플레이어 기준으로 시계 방향 이동한다.
- 스몰 블라인드와 빅 블라인드도 생존 플레이어 기준으로 결정한다.
- 블라인드를 낼 칩이 부족한 경우 가능한 만큼만 지불하고 즉시 `ALL_IN` 상태가 된다.
- 홀카드 2장을 각 플레이어에게 분배한 뒤 프리플랍 액션을 시작한다.

## 12. 액션 규칙

가능한 액션은 다음과 같다.

- `fold`
- `check`
- `call`
- `bet`
- `raise`
- `all-in`

세부 규칙은 다음과 같다.

- `check`는 추가로 맞춰야 할 금액이 0일 때만 가능하다.
- `call`은 현재 필요한 금액 이상을 보유한 경우 정상 call로 처리한다.
- 필요한 금액보다 적은 칩만 남아 있으면 all-in call로 처리한다.
- `bet`은 현재 라운드에 선행 베팅이 없을 때 가능하다.
- `raise`는 현재 베팅이 존재할 때 가능하다.
- 정상 raise는 최소 raise 폭을 만족해야 한다.
- `all-in`은 자신의 남은 스택 전부를 거는 액션이다.
- all-in 금액이 최소 raise 조건을 만족하지 않아도 유효한 액션으로 인정한다.
- 다만 이 경우 다음 플레이어의 재오픈 권한은 표준 규칙에 따라 판단한다.
- `ACTIVE` 플레이어만 액션을 낼 수 있다.
- `ALL_IN`과 `FOLDED` 플레이어는 추가 액션을 하지 않는다.

## 13. 베팅 라운드 종료 규칙

현재 라운드는 다음 조건 중 하나를 만족하면 종료한다.

- `ACTIVE` 플레이어가 1명만 남은 경우
- 모든 `ACTIVE` 플레이어가 현재 유효 최고 베팅 금액을 맞춘 경우
- 남아 있는 플레이어 구성이 `ACTIVE`와 `ALL_IN`뿐이고 추가 액션이 더 이상 불가능한 경우

추가 액션이 불가능하고 `ALL_IN` 플레이어만 쇼다운 대기 중이면 남은 커뮤니티 카드를 자동 오픈한다.

## 14. 메인 팟과 사이드팟 규칙

- 사이드팟은 올인으로 인해 플레이어별 기여 금액이 달라질 때 생성된다.
- 서버는 각 플레이어의 총 기여 금액을 기준으로 낮은 금액부터 계층별로 팟을 분리한다.
- 모든 생존 플레이어가 공통으로 넣은 최소 금액 구간은 메인 팟이 된다.
- 그보다 더 많이 낸 플레이어들 사이의 초과 금액은 순차적으로 사이드팟이 된다.
- 각 팟은 해당 팟에 실제로 기여한 플레이어만 우승 경쟁 대상이 된다.
- 팟 구조는 서버가 계산하며, 클라이언트는 `mainPot`과 `sidePots` 배열을 그대로 렌더링한다.

## 15. 쇼다운 및 정산 규칙

- 리버 종료 후 `ACTIVE` 또는 `ALL_IN` 플레이어가 2명 이상이면 쇼다운을 진행한다.
- 서버는 족보 비교를 통해 각 팟의 승자를 판단한다.
- 결과 스냅샷과 결과 이벤트에는 쇼다운 참가 플레이어별 족보명을 포함한다.
- 동일 팟에서 동점이 발생하면 해당 팟을 균등 분배한다.
- 정수 나눗셈 후 남는 칩은 딜러 버튼 기준 시계 방향으로 먼저 만나는 승자에게 1칩씩 배분한다.
- 정산 후 스택이 0이 된 플레이어는 `BUSTED_OUT` 상태로 전환한다.
- 핸드 종료 후 토너먼트 상태는 `HAND_RESULT`로 5초간 유지한 뒤 다음 핸드 또는 종료 상태로 전환된다.

## 16. 토너먼트 종료 조건

- 생존 플레이어가 1명만 남으면 즉시 토너먼트를 종료한다.
- 마지막 생존 플레이어를 우승자로 선언한다.
- 토너먼트 상태를 `FINISHED`로 변경한다.
- `FINISHED` 상태에서는 더 이상 액션을 받지 않는다.
- 결과 화면에서는 우승자 닉네임과 최종 스택을 표시한다.

## 17. 연결 끊김 정책

- `WAITING`에서 연결이 끊긴 플레이어는 즉시 테이블에서 제거한다.
- 핸드 중 `ACTIVE` 플레이어가 연결이 끊기면 서버는 해당 플레이어를 즉시 fold 처리한다.
- 이미 `ALL_IN` 상태였다면 액션 없이 그대로 쇼다운 대상에 유지한다.
- 토너먼트 진행 중 연결이 끊긴 사용자는 같은 `guestId`로 재연결할 수 있다.
- MVP에서는 좌석과 토너먼트 스냅샷만 복구한다.
- 세밀한 타임뱅크 복원은 지원하지 않는다.

## 18. 최소 API 및 이벤트 계약

필수 REST API 예시는 다음과 같다.

- `POST /api/v1/guests`
- `POST /api/v1/tournaments`
- `POST /api/v1/tournaments/{code}/join`
- `GET /api/v1/tournaments/{code}`

필수 WebSocket SEND 목적지는 다음과 같다.

- `/app/tournament.ready`
- `/app/tournament.start`
- `/app/game.action`

필수 SUBSCRIBE 목적지는 다음과 같다.

- `/topic/tournament.{code}`

필수 브로드캐스트 이벤트는 다음과 같다.

- `tournamentSnapshot`
- `readyChanged`
- `levelChanged`
- `handStarted`
- `actionApplied`
- `potsUpdated`
- `showdownStarted`
- `handEnded`
- `playerBusted`
- `tournamentFinished`

## 19. UI 최소 요구사항

- 테이블 화면에는 최대 9석 레이아웃이 있어야 한다.
- 현재 블라인드가 표시되어야 한다.
- 다음 블라인드까지 남은 시간이 표시되어야 한다.
- 각 플레이어 스택이 보여야 한다.
- 팟 정보와 사이드팟 정보가 보여야 한다.
- 내 액션 버튼 영역이 있어야 한다.
- 플레이어가 `ALL_IN` 상태가 되면 좌석에 명확하게 표시해야 한다.
- 쇼다운 시에는 각 팟별 승자와 분배 금액을 결과 패널에 표시해야 한다.
- 쇼다운 시에는 공개된 플레이어별 족보명을 결과 패널에 표시해야 한다.

## 20. 구현 단계 로드맵

1. 토너먼트 도메인과 상태머신 구현
2. 블라인드 레벨 타이머와 핸드 시작 로직 구현
3. 올인과 사이드팟 계산 구현
4. 쇼다운과 팟 분배 구현
5. 탈락 처리와 우승자 판정 구현
6. 프런트 테이블 UI와 이벤트 바인딩 구현

단계별 보강 포인트는 다음과 같다.

- 1단계: `Tournament`, `TournamentLevel`, `TournamentPlayer`, `HandState`, `Pot` 구조를 먼저 정의한다.
- 2단계: 레벨 상승은 다음 핸드부터 반영되도록 구현한다.
- 3단계: 가장 복잡한 부분이므로 별도 단위 테스트를 충분히 작성한다.
- 4단계: 메인 팟과 여러 개의 사이드팟을 독립적으로 정산한다.

## 21. 최종 판단

토너먼트만 먼저 구현하고 캐시 게임은 나중에 추가하는 방향은 합리적이다. 다만 토너먼트를 선택한 이상 올인과 사이드팟은 후순위로 미루기 어렵다.

따라서 현재 프로젝트의 다음 목표는 캐시 지원이 아니라 다음 항목을 먼저 안정화하는 것이다.

- 토너먼트 상태 모델
- 블라인드 레벨 시스템
- 올인 및 사이드팟 정산 엔진
